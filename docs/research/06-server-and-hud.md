# Сервер, клієнт і інтерфейс гри

## Одиночна гра — це теж клієнт і сервер

Ключова річ, без якої порт не має сенсу: **у BF2 світом володіє сервер
навіть офлайн**. Рушій піднімає локальний сервер і під'єднується до нього.
Тому серверна частина — не «мультиплеєрна добавка», яку можна відкласти, а
ядро: клієнт лише показує те, що йому надіслали.

Це видно і зі структури вихідників, відновленої з `BF2_r.exe`:
`BF2/Game/GameServer/`, `BF2/IO/Network/ProtocolLayer/{NetServer,NetClient}.cpp`.

## Як зроблено в нас

Канал абстрактний (`net::Connection`): для одиночної гри це петля в пам'яті,
для мережі буде UDP. **Формат пакетів однаковий** — інакше одиночна гра
перевіряла б не той код, який потім працює в мультиплеєрі.

```
клієнт -> сервер : ConnectionRequest      версія протоколу + ім'я гравця
сервер -> клієнт : ConnectionAccept       id гравця, рівень, режим
                   або ConnectionDenied   код причини
клієнт -> сервер : ConnectionAcknowledge
сервер -> клієнт : Data                   поява й оновлення об'єктів
```

Стан світу йде **лише після підтвердження** — інакше клієнт отримував би
об'єкти ще до того, як дізнався свій id і назву рівня. На це є окремий тест.

Позиції передаються стисненим вектором із `docs/research/04-netcode.md`,
кути — 16 біт на вісь.

## Перевірка: рівень малюється з мережі

```bash
./build/macos-arm64-debug/src/app/openbf2 --level Dalian_plant --hosted
```

```
локальний сервер: InWorld, гравців 1, пакетів 77/2
клієнт отримав об'єктів: 907 з 907
унікальної геометрії: 132, розставлено: 906
```

З `--hosted` розстановка береться **не з файлу рівня**, а з пакетів, які
прийшли від сервера. Картинка збігається з прямим завантаженням — отже
протокол не втрачає й не спотворює нічого.

Дорогою знайшлася справжня помилка: імена шаблонів обрізалися на 32
символах, і три об'єкти (`fence_corrugated_3x12m_broken_parts` та інші)
приходили без геометрії. Довжину піднято до 64, а порція появ у пакеті
зменшена з 24 до 12, щоб пакет лишався в межах 1200 байтів.

## Інтерфейс: Flash тільки в головному меню

Перевірка `Menu_client.zip` змінила картину, яку ми мали:

| Тека | Файлів | Що це |
|---|---:|---|
| `HUD/` | 1145 | **декларативний GUI у `.con`** |
| `External/FlashMenu/` | 1093 | Flash: 5 `.swf` плюс PNG-ассети |
| `Nametag/`, `Atlas/`, `Console/` | 27 | дрібниці |

Тобто **весь ігровий інтерфейс — це `.con`, а не Flash**: HUD, табло, екран
появи, список рівнів, відомості про сервер. Flash лишається виключно в
головному меню до входу в гру.

Вузол оголошується так:

```
hudBuilder.createPictureNode IngameHud WarningIcon 701 292 32 32
hudBuilder.setPictureNodeTexture Ingame/GeneralIcons/.../icon.tga
hudBuilder.setNodeShowVariable WarningIconShow
hudBuilder.setNodeInTime 0.2
```

Далі всі `set*` застосовуються до **останнього створеного вузла** — той
самий принцип, що й у `ObjectTemplate`.

Типи вузлів: `PictureNode` (2375 створень), `TextNode` (1025),
`ButtonNode` (504), `SplitNode` (825), `BarNode`, `ObjectMarkerNode`.
Кнопки мають `setButtonNodeConCmd` — **інтерфейс керує грою консольними
командами**, тобто через ту саму консоль, що читає `.con`.

`obf2::hud` розбирає це у дерево вузлів: 1615 вузлів у 100+ групах
(`IngameHud` 60, `Scoreboard` 38, `MapFilterKits` 32...). 1574 команди ще
без обробника — це наступна порція роботи, і вона видна в лічильнику.

```bash
./build/macos-arm64-debug/tools/hud_dump/hud_dump "Game Files/mods/bf2"
./build/macos-arm64-debug/tools/hud_dump/hud_dump "Game Files/mods/bf2" Scoreboard
```

## Що це означає для планів

Рішення «Flash через gameswf» лишається чинним, але **терміновість його
впала**: усе, що показується під час гри, малюється нашим власним
інтерфейсом із `.con`. Flash потрібен лише для головного меню, і його
цілком можна замінити власним екраном, поки gameswf не інтегрована.
