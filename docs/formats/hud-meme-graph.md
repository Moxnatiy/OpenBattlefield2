# The HUD animation system is a file, not code

In Refractor 2 the whole interface is a tree of `dice::meme::*` nodes, and it
is **executed**. Nodes with conditions switch branches on and off, layers
shift by variables, effects tint them, and actions move those variables every
frame.

Because of that, what looks like "animation in the engine" actually lives in
`Menu/Ingame` — 3673 bytes over 187 nodes.

## What comes from where

| what | where | in our tree |
|---|---|---|
| the file format | `dice::meme::IStream`, symbols in `MemeDll.dll` | `obf2::meme::File` |
| each class's fields | each class's `onStream`, field names as strings | `classes.inc`, generated by `tools/meme_read.py --cpp` |
| execution | `CullVariableActionNode::onEvent` 0x10004e99 and others | `obf2::meme::Graph` |

The class table is **not written by hand**: `MemeDll.dll` and `MemeBf.dll`
from the mod's directory export full C++ symbols, every `onStream` passes the
field name as a string, and the field's type is whichever stream method was
called. 263 classes, with inherited fields expanded in place. To re-take it:

```
tools/meme_read.py --cpp src/meme/include/obf2/meme/classes.inc
```

## The format

* the header: a version string, then a string dictionary with one-byte
  lengths, up to an **empty** one;
* the root: only a two-byte class number, no size (`Object::loadNew`);
* a nested object: a four-byte **size**, a two-byte name, a two-byte class,
  then the fields (`Object::load`);
* a "string" in a class stream is an index into the dictionary; zero means
  empty.

The size is measured from itself, and it is exactly what the engine uses to
skip the unknown. Ours does the same: the size outranks the field table.

## Execution

The update event has the number **0x16** — visible from the
`*(int *)param_4 != 0x16` check at the start of both actions that move
variables.

```
CullNode::iterateUpdate         0x10004a57   the show pass, In time / Out time
CullVariableActionNode::onEvent 0x10004e99   condition -> run the action
SetVariableAction                            assign
SetVariableSoftAction::onEvent  0x10004d2c   linearly towards a target
SetVariableSineAction::onEvent  0x10001050   the same plus a braking stretch
ActionListAction                             run a list
```

Data expressions: `NotData`, `AndData`, `OrData`, `EqualData`, `ToggleData`,
with `FloatData`, `BoolData`, `FloatRefData` as leaves.

**`ToggleData` returns "Data 1" when the switch is zero.** The order is the
reverse of what one expects, and it is not a slip: `ToggleData::value`
(`MemeDll.dll`, 0x100032a6) reads the switch and takes "Data 1" only on zero;
on non-zero — **and when there is no switch at all** — it takes "Data 2". We
had it the other way round, and the right-hand region picked the wrong
position and the wrong alpha.

**Only a leaf turns a name into a variable.** It is leaves that the engine
binds to the HUD object's fields (`BF2.exe`, 0x789480 registers fields under
such names). For a composite node the name is just a label: `ToggleData
"BottomRight/BottomRight_NextPos"` has to be computed, not read from the
store.

The variables' initial values sit in the file itself: the `Value <do not
edit>` of a named leaf is what the variable starts from.

## The corner regions

`Menu/Ingame` gives them as a "moving + static" pair. The moving one is a
`BfTransformNode` whose X and Y are **data nodes**, so X can be bound to a
variable; the static one is a plain `TransformNode` in the `Next node` field.

| region | X | Y | size |
|---|---|---|---|
| BottomLeftAnimate | `BottomLeft/BottomLeft_XPos` | 563 | 400x64 |
| BottomLeftStatic | -1 | 563 | 400x64 |
| BottomRightAnimate | `BottomRight/BottomRight_XPos` | 497 | 600x100 |
| BottomRightStatic | 401 | 563 | 400x64 |

Until now we kept these four regions as numbers in `main.cpp`. The numbers
matched the file to the last one — now they are taken from it
(`Graph::layers`).

The speeds come from there too: `SetVariableSineAction {Speed 600}` drives the
position, `SetVariableSoftAction {Speed 10}` the alphas. The braking stretch
is zero in both, so the motion is linear.

## The division of labour

The same as in the game:

* the **client's state machine** (`BF2.exe`, 0x78b600 for the left region)
  reads the current values and writes the **targets** — `BottomLeft_nextXPos`,
  `nextAlpha1`, `nextAlpha2`;
* the **graph** moves the values towards the targets every frame.

## What is still missing

* `VariableColorEffect` (11 of them in the file) — node colour and alpha from
  variables. The plates are supposed to be tinted through it; for now we draw
  the colours from `.con`.
* `AlphaFadeEffect`, `ShowEffectNode` — branch fading.
* `PictureNode` in the graph itself (11 of them) are **test squares** 20x20
  under `BoolData "showTest"`, not HUD artwork: they have no texture, only a
  colour from `VariableColorEffect`. That is why the effects themselves have
  no visible consequences yet.
* Who sets `BottomRight_direction` to one — **the source has not been
  found**. The matching "hide" was found (0x7a8280), the "show" was not.


## The right region: a machine of five nodes

The `BottomRightAnimate` region is driven not by one variable but by a chain
of five `CullVariableActionNode` in the file itself. Each such node is "while
the condition holds, run the action"; they go from the outermost to the
innermost, and that is the order in which the actions run per tick.

| # | condition | action |
|---|---|---|
| A | `AniPos AND (alpha == oldAlpha OR direction)` | `SetVariableSineAction {600}`: `XPos` -> `NextPos` |
| B | `AniPos` | the same for the left region |
| C | `AniPos` | `SetVariableSoftAction {10}`: `alpha` -> `nextAlpha`, and the two left alphas |
| D | `XPos == oldXPos AND setDirection` | `setDirection` := 0 |
| E | `NOT direction` | `setDirection` := 1 |

where `NextPos = Toggle(direction){newXPos, oldXPos}` and
`nextAlpha = Toggle(setDirection){newAlpha=1, oldAlpha=0}` — bearing in mind
that "Data 1" is taken on **zero**.

Together that gives:

* `direction = 1` — the region travels to `oldXPos`, and **the moment it
  arrives** D clears `setDirection`, after which C fades it in to 1;
* `direction = 0` — E sets `setDirection`, C fades the region out to 0, and
  **only once faded** does it travel to `newXPos` (until then condition A is
  held shut by `alpha != oldAlpha`).

`setDirection` is a purely file-side variable, the engine never touches it.
The other three are bound to the HUD object's fields — see
docs/functions/hud-bottom-right.md.

The one-tick delay between `direction` and the alpha is real: `setDirection`
is set by the innermost node E, while the alpha is read by C, which runs
earlier. That is covered by the test in `tests/test_meme.cpp`.
