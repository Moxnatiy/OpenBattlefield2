# Sprite particle systems — Retail 1.50, RendDX9.dll

`SpriteParticleSystem` templates (smoke, fire, explosion flashes, impact
puffs) are simulated and drawn by the renderer DLL, not by `BF2.exe`.
`BF2.exe` only forwards each `ObjectTemplate.<field>` to a virtual setter on
the renderer's template. Addresses are preferred RendDX9.dll addresses
(`evidence/retail-captures/m4-effects-20261120/RendDX9.dll`, the headless
project `ghidra_projects/headless/RendDX9`).

Port: `src/app/include/obf2/app/sprite_particles.h`,
`src/app/src/sprite_particles.cpp`, test `tests/test_sprite_particles.cpp`.

## Template types, 0x100d5280 and 0x100d4320

`ParticleSystemManager` creates a template by type (0x100d5280) and an
instance for it by the template's type (0x100d4320):

|---|---|---|---|

| 1 | 0x10179dd0 / 0x238 / 0x1021f898 | 0x101849f0 / 0x224 / 0x10220058 | 0x10185f40 |
| 2 | 0x10188130 / 0x250 / 0x10220308 | 0x1017b7d0 / 0x19c / 0x1021fbc0 (TrailSystemInstance.cpp) | 0x1017be70 |
| 3 | 0x10186cb0 / 0x1a8 / 0x10220150 | 0x101823e0 / 0x220 / 0x1021ff60 | 0x10183910 |
| 4 | 0x10178b90 / 0x27c / 0x1021f5b8 | 0x1017d600 / 0x228 / 0x1021fd48 | 0x1017e870 |

**Type 0 is the screen-aligned sprite.** Its draw collectors 0x10171000 and
0x10171d20 (chosen by `particleType`, 0x10176150) feed the vertex writer
0x10170070, which selects the `Particles.fx` techniques
`ParticleShowFill/Low/Medium/High` from the global quality at
manager+0x8cac. Type 4 has the same control flow (0x1017e870, integrator
0x1017cdc0, spawn 0x1017dcb0) but its records carry four 3-D corners and are
written by 0x1016dbb0 (stride 0x48), the non-screen-aligned path. An earlier
pass decoded type 4 first; every number below is type 0.

## Field → template offset (type 0)

`BF2.exe` registers one descriptor per field (`FUN_0056xxxx`, string xref);
descriptor vtable slot +0x5c calls a forwarder (`FUN_0064xxxx`) that calls
virtual slot N on the renderer template held at BF2 object+0x9c. The slot
resolves through vtable 0x1021f300 to the setter. Where a field name has
several registrations (sprite, mesh particle, NSA classes) the one used is the
one whose offset the type-0 spawn 0x101801c0 and integrator 0x1017f520 read.
Generated by a headless script over both binaries; reproducible with
`FieldSlots.java` (notes in this file's history).

## Instance update, 0x10180ba0

Per frame with `dt` (times the instance's time scale +0x12c):

1. Clamp the frame step to `timeToLive + randomTimeToLive` (+0x84 + +0x80).
2. **Fixed steps.** `n = round(100 · (dt + carry))` (constant 100.0 at
   0x1021fe40); `carry = dt + carry − n·0.01` (0.01 at 0x1023a478);
   instance clock `now += n·0.01`. Every live particle is integrated by
   0x1017f520 with `n` steps of 0.01 s.
3. **Delay.** `delay −= dt` (+0xe4). While positive, `lastEmit = now` and
   return — no emission.
4. **Emission**, 0x10180790. `rate = emitFrequency · scaleA · scaleB`, the
   then, only when the system loops or instance +0xe8 > 1, and only when the
   manager byte +0x1d3c is set **or** the manager's live particle count
   (+0x5f28) is above `round(budget +0x5f24 · fraction +0x8c08)`, times the
   quality multiplier manager+0x8bfc[emitPrio] (0x10180893, indexed
   directly: emitPrio 0, 1, 2 → +0x8bfc, +0x8c00, +0x8c04). The manager
   constructor (0x100d5df0, stores at 0x100d6060..) sets +0x8bf8 0.85,
   +0x8bfc 0.40, +0x8c00 0.55; the quality setter 0x100d3d20 overwrites
   +0x8bfc..+0x8c04 from its settings record words 4..6 (+0x8bf8 from word
   11, a separate value read by 0x100d3590). Under light load the gate is
   closed and the rate is unscaled; the port has no manager budget and
   keeps it unscaled. What +0x1d3c is (a byte of the sub-object built by
   0x10171430 at manager+0x108, its +0x1c34) is **not established**;
   then `rate = max(rate, +0x14)`; `interval = 1/rate`. While
   `lastEmit + interval ≤ now`: if remaining emit time (+0xe0) is nonzero,
   subtract `interval`; when it reaches ≤ 0 call stop (virtual +0x10), and if
   `isLooping` restart (virtual +0xc), then return. Otherwise
   `lastEmit += interval`, spawn (0x101801c0) at the emitter position
   interpolated between last frame's and this frame's by
   `(lastEmit − prevNow)/(now − prevNow)` (0x101070c0), add the instance's
   inherited velocity (+0x18..+0x20) and integrate the new particle forward by
   `round((now − lastEmit)·100)` steps, then once more by the remainder.
   A particle is only spawned while the instance is active (+0x128) and below
   its cap +0x220 (live count +0x28 below it). The instance constructor
   0x1017fb00 sets the cap to `round(span · emitFrequency + 10)` (10 at
   0x101e2b00), `span = timeToLive + randomTimeToLive`, or
   `min(emitTime, span)` when emitTime (+0x1d4) is not 0 and `isLooping` is
   clear; it allocates `cap·4 + 4` bytes for the record pointers. Port:
   `SpriteEmitter::particleCap`.
5. Pre-warm (byte +0x269 set): on activation the instance is updated in
   0.1 s pieces for `timeToLive` seconds. What sets +0x269 is **not
   established**; the port does not pre-warm.

## Integrator, 0x1017f520

Record fields used: +0x48 position, +0x60 velocity, +0x6c age, +0x70 ttl,
+0x74 1/ttl, +0x24 age factor. With `h = 0.01`, `n` steps:

```
age += n·h;               if age ≥ ttl: free the record
t    = ageFactor          (the value from before this call)
k    = clamp01(airResistanceGraph(t)) · airResistance · h
g    = clamp01(gravityGraph(t))
ageFactor = age / ttl
repeat n:
  rel = velocity − wind
  dv  = |rel| > 1.19e-7 ? −rel · |rel| · k : 0      (quadratic drag)
  dv.y += g · h · gravity                           (positive gravity rises)
  position += (velocity + dv/2) · h
  velocity += dv
zero each velocity component with |v| < 0.001
```

Taken apart with `tools/ghidra_scripts/DecompileAt.java`,
`DisasmRange.java` and `FieldOffsetUsers.java` over the headless RendDX9
project (the last lists every `[reg+offset]` of a field across a range).

**Wind** (before the loop, once per call): `wind = windManager(position) ·
windAffectionFactor`, where the manager is +0x8c0c of the particle manager
(virtual +0x3c, takes the record position +0x48). It is zero unless the
global flag +0x8c10 is set, template byte +0x21d is clear, and
`windAffectionFactor > 0`. +0x21d has a getter at 0x101777e0; its field name
is **not established**. When set, it also transforms the drawn position by
the instance matrix (+0x74..+0xac) — a local-space system.

**Collision** (after the loop, `collisionEnable`). The instance keeps its
current plane at +0x208 (n, d), a ring of ten older ones at +0x168 (0x10
each), the current index +0x218, the next +0x219 and a clock +0x21c. The
update 0x10180ba0 adds the unclamped frame step to the clock and calls
0x10180120: when the clock reaches 0.33333 (0x1021fe18) it subtracts that,
copies the current plane into slot +0x219 with the normal normalized
(0x10077e90), makes that the current index and advances +0x219 mod 10 (once
per update). The integrator picks a plane by the record's age:
`behind = clock − age`; if `behind < 0`, index `cur − round(−3·behind) − 1`
(−3.0 at 0x1021fe14) wrapped into 0..9; when that equals `cur`, or
`behind ≥ 0`, the current plane +0x208. Then, if `v·n < 0` and
`dist = p·n + d < 0`: `p −= dist·n`; with `vn = v·n` (still < 0),
`v = (v − vn·n)·collisionSpeedAlongPlane − vn·n·collisionSpeedAlongNormal`
(+0xf4, +0xf0). The instance ctor 0x1017fb00 sets the current plane +0x208
and all ten ring slots (+0x168..+0x204) to (0, 1, 0, 0), the y = 0 ground
plane, and +0x218, +0x219 and +0x21c to 0. So an instance that is never given
a plane still collides with y = 0. Who sets +0x208 later is below.

**Drawn position.** Record +0x54 bit 7 is set (the per-frame pass
0x10172450 runs only on records with it, and clears it); +0x18 = position.
If `forceToWaterSurface` (+0xa8) and the water object (manager +0x8c14) is
present, +0x18.y = its virtual +0x94 at +0x18. The simulated position keeps
its own y. Then 0x1017a4b0 grows the instance bounds. `waterSurfaceOffset`
(+0xac, ctor 0.03 at 0x101764c5) is read by no type-0 function; only its
getter 0x101776e0 (vtable 0x1021f428) touches it, whose caller is not found.

**Wind time scale** (update 0x10180ba0, 0x10180d70..0x10180e33): when +0x21d
is clear, template +0xb0 ≥ 0 and `windAffectionFactor ≥ 0`, instance +0x130 =
`max(clamp01(|wind|²/max(+0xb4², 1)) · +0xb0, 1) · timeScale(+0x12c)`, with
the wind at the emitter (0x10027bd0 is the squared length); otherwise
+0x130 = +0x12c. It does not check the global wind flag. Setters 0x10177830
(+0xb0, slot +0x268, ctor 0) and 0x10177810 (+0xb4, slot +0x260, ctor 10);
no BF2.exe forwarder in 0x640000..0x660000 calls those slots, so their field
names are not traced. No type-0 function reads +0x130; the type-4 per-frame
0x1016f190 multiplies by it (0x1016f54b). Port:
`SpriteEmitter::windTimeScale()`.

**Where the inputs come from.** Wind: manager +0x8c0c is the named object
`WindManager` (0x100d33b0, string 0x101e02c4); its slot +0x3c is
`WindManager::getWind` (BF2.exe 0x729720), taken apart in
docs/functions/wind.md and ported as `game::WindManager`. The flag +0x8c10
starts at 1 (0x100d609e); a console command toggles it (0x100bc5f6). Water:
manager +0x8c14 is the named object `HeightmapCluster` (0x100d3550, string
0x1020cb28). Its +0x94 (BF2.exe 0x6e20f0) calls +0x98(x, z) (0x6e20a0): inside
the cluster (+0x9c) the heightmap there (+0x4c) answers +0xe0 → 0x6f6460 →
its water-level grid (+0xdc) when it has one, else its sea level (+0x60,
`heightmapcluster.setSeaWaterLevel`, ctor −10000 at 0x6f48f0); outside, 0.
The port uses the sea level (or −10000) everywhere: where a water grid comes
from is not taken apart. Collision plane: instance slot +0x48 (vtable 0x1021fe48, 0x101800e0) stores
(n, d) at +0x208 with n normalized (0x10077e90). **Caller traced** in BF2.exe:
EffectBundle 0x641ba0 forwards a plane to every renderer particle system in
the bundle's list (+0x174, filled by `addBundleChilds` 0x642c70 → 0x642a90).
It is called when a bundle is spawned on a surface:

| caller | plane from |
|---|---|
| 0x5ca910 (from 0x5ca9c0, and 0x5cadf0 — the material-explosion spawner, `decal_mexp_default`) | the spawn matrix built by 0x5ca5f0: row 1 (+0x10) the surface normal, row 3 (+0x30) the point; the identity orientation (row 1 = 0/1/0) when the normal is not at right angles to the forward vector (\|n·f\| > 0x8eaa8c) |
| 0x5a7a50 (from 0x5ab850) | an up vector (0, *0x9ec2b0, 0) turned by the spawning object, through its matrix |
| 0x6e5ef0 (from 0x6e6c80, twice) | its normal and point arguments |
| 0x646540 (bundle update) | the bundle's own placement against its parent |

All build the plane with 0x5a6bd0: `(n, −n·p)`; only bundles of class
0x91c1e4 or 0x91c21c take it. 226 shipped `.tweak` files enable
`collisionEnable` (ambient and damage-state fire, sparks; no grenade emitter).

Port: `SmokeFlare::observe(…, surface)` passes the plane to every emitter of
the new instance. The tank-shell impact passes the terrain or wall contact's
normal and point; network detonations carry no surface normal (the record's
`vector` is not established as one), so they keep the ctor's y = 0 plane,
as Retail's do when no plane is set. The port's ring starts as the ctor
leaves it (`SpriteEmitter::kGroundPlane`).

## Spawn, 0x101801c0

Random numbers come from 0x1009f860, a 31-bit combined generator
(multipliers 0x5e30 and 0x661f, modulus 2³¹−1). With `q = ((u | 0x80) >> 7) + 1`:
symmetric `q·2⁻²³ − 1` (0x1021fe20), unit `q·2⁻²⁴` (0x1020cf68), the emitter
shape's angles `q·π·2⁻²³` and `q·π·2⁻²⁴`.

In call order:

| value | formula |
|---|---|
| start frame | `animationRandomizedStartFrame ? floor((frameCount−1)·unit) : 0` |
| ttl | `unit·randomTimeToLive + timeToLive` |
| age | instance+0xd8 (0 at start) |
| intensity | instance+0x15c (**not measured**; 1) |
| pivot | `pivotOffset` |
| alpha base | instance+0x160 (**not measured**; 1) |
| shadow | `selfShadowIntensity` |
| size term `r` | `r = symmetric`; `randomSize · r` |
| intensity term | `symmetric · randomIntensity` |
| angle | `symmetric · randomRotation` (radians, used as is) |
| spin | `s = symmetric · randomRotationSpeed`; `s ± rotationSpeed` with the sign of `s` |
| offset (type 0 shape, 0x101813d0) | `a, b` angles, `u, v, w` unit: `(cos a·v·rx·sin b, sin a·u·ry·sin b, cos b·w·rz)` |
| direction | `emitDirection · instance scale (+0x150)`, then rotated by `X(symmetric·rda.x°)`, `Y(symmetric·rda.y°)`, `Z(symmetric·rda.z°)` (0x10078490, 0x1017c470, 0x10079bf0), row-vector order |
| speed | `clamp01(emitSpeedGraph(te)) · (emitSpeed − r·randomSpeed) · instance+0x13c`, `te = 1 − remaining/emitTime` (0 when emitTime ≤ 0) |

The speed reuses `r`, the size term's random number (disassembly
0x1017e0d3 for type 4; the type-0 decompile has the same expression), so large
particles are slower when `randomSpeed > 0`. The composition order of the three
rotations is the call order; that each call post-multiplies is **inferred**.

## Per frame, 0x10172450

`g = clamp01(rotationGraph(ageFactor))`, `dt` the frame step (+0x1c3c):

Runs only on a record the collector accepted, and only when record +0x54
bit 7 (set by the integrator) is set; it clears the bit.

* `alignRotationToSpeed` off: `angle = fmod(angle + g·dt·spin, 2π)`
  (2π double at 0x1020aae8; operands from the type-4 twin 0x1016f37c).
* `alignRotationToSpeed` on (+0x21c): with `p` the drawn position and
  `q = p − velocity·0.001` (0x101dde54), both through the view matrix at
  renderer +0x1c98 (rows 0x10 apart; x, y and the depth z) and divided by z
  (0 when |z| ≤ 2⁻²², 0x1021ef14): `dx, dy = proj(p) − proj(q)`. Length ≤ 2⁻²²
  → angle 0. Otherwise `a = acos(clamp(dy/len, −1, 1))` (0x100a6890);
  `angle = dx ≤ 0 ? 2π − a : a` (2π at 0x101e2b9c). The spin is not applied.
* Rotation index: `round(angle · 651.899)` (4096/2π, 0x1021ef10; 0x1016f8a0
  rounds) `& 0xfff` → record +0x88; record +0x3c = renderer table +0x1e14
  entry. The table (0x10171a58, 4096 entries): low short
  `_ftol(sin(i·2π/4096)·32767)`, high short the cos (0x1021ef18, 0x10219558,
  _ftol 0x101c4c64). Port: `quantizedRotation`.
* Animation (`animationEnable` and `frameCount`): `frame += g·dt·animationSpeed`;
  index `floor(frame) mod frameCount`, blend `frame − floor(frame)`.

## Drawing, Particles.fx and 0x10170070

Per vertex (stride 0x40): position, age factor, random size term, alpha
factor, frame blend, displacement `(±1 − pivot)` (−1 at 0x1021edc4), intensity
and its random term, rotation as shorts, frame UV offsets, texcoords ±32767.

```
t      = ageFactor;  pc = (t³, t², t, 1)
blend  = min(colorBlendGraph·pc, 1)
rgb    = (color2·blend + color1·(1 − blend)) · intensity + intensityTerm
alpha  = min(transparencyGraph·pc, 1) · alphaFactor
size   = min(sizeGraph·pc, 1) · particleMaxSize + sizeTerm      (half extent)
corner = viewPosition + displacement · size
uv     = frame cell, central 1/√2 of it (uvScale), rotated by angle
```

**Texcoord rotation** (Particles.fx:69-89). The quad's displacement is not
rotated: the six vertices (two triangles) carry texcoords (±32767) matching
their displacement corner, and the shader turns those:
`r = (tx·cos − ty·sin, tx·sin + ty·cos)` with `rotation = (sin, cos)` from
record +0x3c, scales by `uvRange · uvScale`, biases `u = uvRange.x + r.x`,
`v = uvRange.y − r.y`, halves and adds the frame offset. So the screen
footprint stays an upright square and the image turns inside it. Port: the
quad is screen-aligned; `SmokeFlare::draw` passes sin/cos in
`particleFrame.w`/`particleColor.w`, uv2 holds each corner's offset from the
cell centre, and the mesh vertex shader rotates it (identity at sin 0).

**Self-shadow.** The vertex writer puts the record's intensity (+0x0c) on
the two top corners and `min(+0x08, +0x0c)` — the self-shadow
(`selfShadowIntensity`, copied at spawn 0x101802ef) — on the three bottom
vertices (texcoord y −1) (0x10170070). Port: `SpriteDraw::shadowColor`,
drawn through `DrawItem::particleShadow` (w = 1): the mesh vertex shader marks
the bottom corners (uv2.y > 0) and the fragment stage mixes the two colours
by the interpolated share; checked in `test_particle_blend_gpu`.

**Lighting.** `lightMapIntensityOffset` (+0x144) reaches
`m_uvRangeLMapIntensiyAndParticleMaxSize.z`; the vertex shader makes
`lmOffset = saturate(clamp((y − hemiShadowAltitude)/10, 0, 1) + it)`
(Particles.fx:62); `calcParticleLighting(lm, lmOffset, lightFactor) =
lerp(1, lerp(effectShadowColor, effectSunColor, saturate(lm + lmOffset)),
lightFactor)` (FXCommon.fx:56-62), with `lm = 1` in ParticleMedium and the
hemi map's alpha in ParticleHigh.

`lightFactor` is template +0x168 (m_color1AndLightFactor.a; the color1
setter 0x101769a0 fills +0x15c..+0x164). The type-0 finaliser 0x10177160
(vtable 0x1021f300 slot +8) sets it to template +0x1f8 when that is ≥ 0,
else to LightManager (DAT_1024b914) virtual +0x270. +0x1f8 is written by the
setter 0x10176320 (slot +0x18c), which the ctor init 0x101763e0 calls with
−1.0. **Traced:** BF2.exe registers `ObjectTemplate.LightAffectionFactor`
at 0x56d208; its set branch 0x56d2c6 calls the forwarder 0x64f650, which
calls slot +0x18c on the renderer template. The RendDX9 console command
`defaultEffectLightAffectionFactor` (0x100be2fc) reads back through
0x100be3ba, which calls the same LightManager +0x270. No grenade template
sets the factor, so Sky.con's default applies (FuShe Pass: 1).

### Hemi map

`hemiMapManager.setBaseHemiMap <path> <centre> <size> [height]`
(command 0x100c4aea, execute 0x100c4bcd; with three arguments the height is
the constant at 0x1021731c) calls HemiMapManager (DAT_1024b904, vtable
0x1021ce84) +0x14 = 0x1012c2a0, which frees the old data and builds new with
0x1012b930: +0x00 centre (3 floats), +0x0c size, +0x10 height, +0x14 the
texture `<path>.dds`, +0x18 the path. A file that does not load becomes an
8×8 texture of 0xffffffff (0x1012ba13). The particle renderer's per-frame
upload 0x101721c0 takes the data from +0x18 (0x1001a1e0, the manager's +8)
and, when present, sets `HemiMapInfo` to +0x1c (0x1012b620) =
(centre.x, centre.z, size, manager +0x1c), `HemiShadowAltitude` to the
height and `Texture1` to the texture; without data, Texture1 is the fallback
0x100f1bf0(0), whose contents are not taken apart. Particles.fx:93-94 then
samples `lutSampler` (LINEAR, CLAMP, FXCommon.fx:43-51) at
`((pos + size/2).xz − centre.xz) / size`, v flipped, with `pos` the record
position on all six vertices — so one value per sprite at mip 0.

FuShe Pass: `Levels/FuShe_Pass/groundhemi` (1024², DXT3), centre 0/0/0, size
2048, height 500.

Port: `app::HemiMap` (`hemi_map.h`) loads it in `WorldView::init`, and
`SpriteEmitter::collect` takes `lm` from it (ParticleHigh, which Retail draws
at effects quality 2). Without `setBaseHemiMap` the port uses lm = 1.
`SpriteDraw::light` is folded into both colours in `SmokeFlare::draw`: the
value is constant over the sprite.

Shader models: the effect compiler defines `LOWPSMODEL` as `ps_1_4`
(RendDX9.dll 0x1003641f–0x10036451, define pair at 0x101e1298/0x101e129c), so
`ParticleLow/Medium/High` read the colour through `texcrd`, unclamped. The
`Additive*` techniques compile `ps_1_3` (Particles.fx:326,350), whose `texcoord`
read saturates to [0, 1]: there the colour factor tops out at 2. No grenade
colour exceeds that; the port does not clamp yet.

FuShe Pass sets `Lightmanager.effectSunColor` and `effectShadowColor` to
1/1/1 (`Levels/FuShe_Pass` Sky.con), so `calcParticleLighting` is 1 on that
map and the Low technique the port draws is exact there.

`Anim_smoke2.dds` (the grenade dust and smoke) is near-white (RGB ≈ 235) with
low alpha (mean ≈ 0.24 over the sampled 1/√2 window of each cell): a single
smoke sprite is faint in both games; density comes from overlap.

`Particle*` techniques: alpha blend, no depth write, no culling.
`Additive*`: ONE/ONE with `rgb ·= texture.a · alpha`, no fog. Low quality uses
one frame; Medium/High lerp two frames and multiply by
`calcParticleLighting`. The port draws Medium's lighting (lm = 1) with
High's two-frame blend.

## Collectors, 0x10171d20 (sorted) and 0x10171000 (additive)

The template is the third argument; `lodDistance` is template +0x64 (ctor 2,
0x10176447). For each record, `d = drawPosition · plane(renderer +0x1c40)`
— taken as the view depth (**inferred**: the plane is not traced) — and
`near` = the camera's virtual +0x34.

1. `d < near`: not collected (both).
2. Additive only: `alphaCull > alpha` (last frame's +0x2c) → not collected.
3. Fade: `d ≤ fadeNear[lod]` → `alpha = alphaBase`; else
   `alpha = (1 − min((d − fadeNear)·fadeScale, 1))² · alphaBase` (+0x2c;
   tables at manager +0x8bec/+0x8be0, measured below).
4. Sorted only: `alphaCull > alpha` → not collected. Then **near culling**
   (`nearCullingEnable` +0x29c, setter 0x10177870): with `dn = d − near`, if
   `dn < 6` (+0x288) and `ageFactor > 0.15` (+0x290):
   `aged = (ageFactor − 0.15)·4 ≤ 1 ? 1 − it : 0` (+0x294),
   `byDist = (6 − dn)·0.5` (+0x28c), `alpha = byDist ≤ 1 ? (1 − byDist) +
   byDist·aged : aged` — replacing, not scaling, the fade; `alpha < 0.01`
   (+0x298) → not collected. The five constants have no setter; the ctor
   0x101763e0 writes them (0x1017648b..0x1017652a).
5. Record +0x14 = squared eye distance; 0x10172450; queue.

`near` is the camera's near plane: vtable 0x1021c968 slot +0x34 returns its
+0x28, which the renderer sets from its +0x590 every frame — 0.041
(0x1002dd16; docs/functions/render-camera.md). Port: `SpriteEmitter::collect`
with a `View`; `SmokeFlare` passes the view and 0.041.

## Template parameters upload, 0x1016fe00

For each of up to ten templates in a batch the renderer copies 0x70 bytes from
template+0x13c (0x10172390, a plain copy) into `TemplateParameters` (handle at
renderer+0x1de8, bound in 0x10171430). The seven vectors are exactly
`Particles.fx` `TemplateParameters`: +0x13c uvRange.xy, +0x144
lightMapIntensityOffset, **+0x148 ParticleMaxSize**, then light colour and
random intensity, colour1 (+0x15c) and light factor (+0x168), colour2, colorBlendGraph
(+0x17c), transparencyGraph (+0x18c), sizeGraph (+0x19c).

`ObjectTemplate.particleMaxSize` reaches +0x148 unscaled: BF2.exe registration
0x56e32e (string `ParticleMaxSize`, 0x8d63c4) → forwarder 0x64f600 → slot 0x164
→ setter 0x10176300 (`this+0x148 = value`). With the vertex writer's ±1
displacement, a sprite's half extent is `size`, as the port draws it.

Every grenade emitter (`e_exp_grenade`, `e_mexp_grenade_gravel`) is
`qualityLevel` Low or Medium, so Retail at effects quality 2 draws all of them;
quality gating does not explain a size difference. How `qualityLevel` gates a
system is not taken apart yet.

### The fireball against the binary and the shader

Checked after the same-spot capture, to find why the port's additive fire
looks harder than Retail's.

**Record fields from spawn (RendDX9.dll 0x101801c0).** The instance's
intensity (+0x15c) is copied to record +0x0c; its alpha base (+0x160) to
record +0x2c and +0x58. Other stores in the same function: +0x78 start frame,
+0x70 ttl, +0x74 1/ttl, +0x6c age, +0x24 age factor, +0x08 template +0xa0,
+0x34/+0x38 template +0x1ac/+0x1b0, +0x28 size term (template +0x1b4),
+0x10 intensity term (+0x1b8), +0x80 angle (+0x1bc), +0x7c spin, +0x60..+0x68
velocity, +0x5c template +0x25c (or `[template+0x260]+0x10`), word +0x90
additive flag. The frame loop later rewrites +0x2c (the distance alpha above).

**Measured in Retail** (`retail-corrugated-grenade-2/trial/sprite-records.txt`,
every record of every snapshot): +0x0c is 1.0 and +0x58 is 1.0 on all
≈ 9 800 records; +0x2c is 1.0 except on the gravel-dust emitters (1.1, 1.2),
where it falls to 0.32–1.0 with distance. So intensity and alpha base are 1,
as the port assumes. The additive emitters (fireflash, glow) are not in the
vectors this script reads (one Additive template, maxSize 0.05, is), so their records are not seen.

**Shader (`Shaders_client.zip`, Particles.fx).** `vsParticle:56` writes
`(colour·intensity + intensityTerm)/2` to a TEXCOORD; `psParticleAdditiveLow`
(`:181`) multiplies the texture by `2·colour` and then by
`texture.a · alpha`; technique `AdditiveLow` (`:305`) is ONE/ONE, no depth
write, no fog, alpha test on with `AlphaRef = alphaPixelTestRef`.
`alphaPixelTestRef` is `0` by default (`FXCommon.fx:17`); no string
`AlphaPixelTest*` occurs in RendDX9.dll, so nothing sets it by name, and no
technique sets `AlphaFunc`. A reference of 0 removes only texels with zero
alpha, which add nothing under ONE/ONE. The `/2 … ·2` round trip clamps the
colour factor to 2 under `ps_1_3`; the fireflash colours are at most 1.

The port computes the same: `rgb · colour · texture.a · alpha`, SRC_ALPHA/ONE
(`mesh_renderer.cpp`, particle branch; `sprite_particles.cpp:292`).

**So nothing in the particle path explains the difference.** Template blocks,
ages, intensity, alpha base and the shader agree. What is left:

* distance: the port's detonation was 8.8 m from the camera, Retail's 6.3 m,
  so the port's sprites are ≈ 1.4× smaller on screen;
* Retail's full-screen blur from the flash on (a camera effect, source not
  found) softens every edge in Retail's stills, the fireball's included;
* timing: the stills are 50 ms apart and aligned on a brightness jump, so
  "brightest at +0.05–0.10 s" against "faded by +0.10 s" is within one
  still of each other.

A frame-matched comparison needs the blur ported or turned off in Retail, and
the detonation at the same distance.

  when template +0x338 (default 0.1) is not 0 and `s` is larger than +0x3c8,
  stores `s` at +0x3c8 and the system time at +0x3d0. The server never reads
  +0x3c8/+0x3d0; the client's reader is **not taken apart**.
* **Tinnitus.** If the player's object is a soldier (0x9493) and
  `d < radius · sound-tinnitus-range`, it calls the sound engine
  `[0xa23dc0]` (BF2Audio.dll `getSoundEngine`, 0x7e1774) slot +0x74, then
  `[0x9ff964]` slot +0x10 with (0, 0xd, sound engine slot +0x70(0)). The
  console command `tinnitusSetup` is registered at 0x7dbe30 (string
  0x93b7bc). How the renderer's Tinnitus timer is started from there is
  **not established**.

**RendDX9.dll, the pass: 0x10051770** (string `Tinnitus` 0x101e2e54; the
post-production framework, `drawPostProduction` 0x10055c80). It runs while
+0x178 is set, +0xfa is clear and +0x1c > +0x10; otherwise +0x164 = 2. It
binds four earlier frames from a ring (indices +0x15c .. +0x15c+3) and the
current one, sets `BACKBUFFERLERPBIAS = (+0x1c − +0x10)/+0x20` and
`SAMPLEOFFSET` to two random values (`rand`-based, 0x101c4c64 through
0x10084560), and draws technique `Tinnitus`. Which of +0x10/+0x1c is the
clock and which the end time is not established, so whether the blend
grows or fades is not either.

**Shader (`Shaders_client.zip`, `PostProduction_r3x0.fx:69-112`):** the four
frames are sampled at the texcoord minus `sampleoffset` and weighted 0.5,
0.25, 0.125, 0.0675; the result is `lerp(accum, backbuffer,
backbufferLerpbias)`. `PostProduction_nv3x.fx:117-191` has the same pass in
two variants. So the blur is a jittered blend of the last frames, which is
what the retail stills show.

**Range.** `Settings/Sound.con:51` sets `vars.set sound-tinnitus-range
1.05` (the 0.6 above is the binary default), so the M67 triggers tinnitus
within 9 · 1.05 = 9.45 m; the camera at 6.3 m was inside. The same file,
line 35: `sound.tinnitusSetup "Common/Sound/tinnitus.wav,Common/Sound/man_down_state.wav" 1 2 4 0.88`;
BF2.exe registers the command at 0x7dbe30 as (string, float, float, float,
float).

**Start and length (RendDX9.dll 0x1004f8e0).** A renderer event (0, 0xd,
data) — the call BF2.exe makes at 0x5cd940 — copies five words from
`data+0x2c` to +0x164..+0x174. When the first is 1, the pass is on (+0x164 is
tested at 0x100519d0) for `n = max(round((w1 + w2 + w3) · 30), 20)` frames:
`+0x1c = +0x10 + n`, `+0x20 = n`. +0x10 is a frame counter, one per drawn
frame (0x100516d0), so the length is in frames, not seconds. The payload
comes from the sound engine (`[0xa23dc0]` slot +0x70(0)). In BF2Audio.dll
the tinnitus object sits at engine +0x1b0 (vtable 0x1003a3d0; setup slot
+0x5c 0x10004760 creates the sound), but `[0xa23dc0]` does not match that
vtable's slots +0x70/+0x74 (0x10004a60 sets, 0x10004a70 returns +0x1b0+0x10),
so it is probably another interface of the engine. **Which setup floats
become w1..w3 is not established.**

**Order.** 0x100519d0 runs inside the scene frame (called from 0x1002cbc5 in
0x1002c2e0). In Retail's blurred stills the HUD hint box and hit arc stay
sharp while the scene behind them smears, so the pass runs before the HUD.

**Measured on Retail** (`retail-corrugated-grenade-2/trial`, edge strength of
the scene below the HUD, 0.05–0.60 × width, 0.35–0.75 × height, per still):
12.3 before, **3.1 on the blast still (frame 94)**, then rising in a straight
line to 12.2 at frame 135, 2.08 s later (QPC 62629061 → 62631141 ms). So the
blur is strongest at once and fades linearly. That is the opposite of reading
`lerp(accum, backbuffer, (end − now)/n)` with sampler 4 as the current frame
(sharp at the start), so what is bound to samplers 0–4 at 0x10051770 is
**not established**. Retail's frame rate during the capture is not measured,
so 2.08 s cannot yet be turned into frames.

The port has none of this: no tinnitus, no explosion camera shake, no
post-production pass. Porting needs w1..w3 and the sampler binding first.
